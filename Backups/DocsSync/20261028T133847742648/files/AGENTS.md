# Vampire Hunter 文档驱动协作规范

项目根目录：`/Users/dorimiah/Desktop/vampire`。日期按 Asia/Shanghai 记录。
当前授权：阶段 1 文档治理 + 阶段 2 的 S01–S13 模板、S01 初稿。不得超出当前用户指令推进。

## 1. 每次工作必读

1. 本文件 → `Docs/PROJECT_STATUS.md` → `Docs/00_Baseline/BASELINE_INDEX.md`。
2. 运行 `python3 Tools/docs_workflow.py check`；失败先报告并处理，不能静默重建基准校验值。
3. 读取根目录 GDD v4 对应规范章节 → F01–F38 登记簿及兼容解释 → SCM 对应主责/协作/契约/测试 → Narrative 对应节拍。
4. 当前系统文档 → `Docs/03_Management/REVIEW_REGISTER.md`、`CHANGE_LOG.md`、相关 CR。
5. 未来开发阶段再读已批准 Project_Plan、Task_Registry、当前唯一 Task ID、批准的技术方案与测试证据。

优先级：用户当前明确指令控制工作范围；设计事实按 GDD v4 规范 > F 最终决策/兼容解释 > GDD 附录旧 R 索引 > Narrative 内容草稿。新冲突先登记，不自行改规则。资源清单仅参考，不能替代设计。

## 2. 文件保护与设计冻结

- 原有 5 份文件原地保留；4 份基准及参考文件的初始 SHA-256 见 Baseline_Manifest。不得覆盖、删除、搬移、重命名或无记录修改。
- 所有设计规则必须引用 R/F 和来源章节；剧情内容区分冻结事件与草案措辞。R03.1 单独追踪；R85 未获选择，不加入设计覆盖分母。
- SCM 的 123/123 只表示责任归属。模板、初稿、用户批准、实现、实测验证必须分别记录。
- S01–S13 均为纯游戏策划：目标体验、操作、可见结果、规则、状态、反馈、边界与场景。不得混入 Unity 类、脚本、插件、导航算法、序列化或工程实现。
- 工程约束仍须追溯 R75/R76/R83 等，放在未来技术设计中；不得因策划去技术化而遗失。

## 3. 阶段与审核门

- 系统状态：Template → Draft → AwaitingReview → Approved。修改已批准文件后，旧批准失效，转 Draft/AwaitingReview 并重新审阅。没有明确用户原话不能 Approved。
- 每次只提交一个系统供审阅。默认顺序沿 SCM：S01 → S02 → S03 → S04 → S06 → S05 → S08 → S07 → S09 → S10 → S11 → S13 → S12。前一份确认后再推进下一份。
- 13 份系统必须逐份得到用户明确批准，且 SHA-256 与当前内容相符，才能生成 Project_Plan.md 和 Task_Registry.md。不得提前创建空计划或大量任务 ID。
- 阶段 3 的计划须包含唯一且不复用的 Task ID、需求/系统关联、依赖、优先级、最小可玩原型、验收条件和测试计划；尊重原 GDD 的序章/墓穴/Boss 原型与全部八房最终范围。
- 阶段 4：读取源文档 → 选 Task ID/检查依赖 → 提出技术方案 → 用户审核 → 实施 → 真实 Unity/自动化测试 → 按证据更新状态。任务授权不等于技术方案自动批准。
- 开发状态独立于设计：NotStarted / InProgress / Testing / Verified / Blocked。代码生成仅可推进 Testing；Verified 必须满足全部验收、记录运行环境与原始结果。静态文档检查不等于 Unity 功能验证。

## 4. 审批与变更

批准记录须包含系统/任务/CR、文件版本、被审内容 SHA-256、用户原话、对话/消息或用户审阅文件来源、日期、批准边界。不能把“继续”“收到”或用户沉默视为整份批准；按实际语义记录。
`workflow_state.json` 是系统/测试状态与批准记录的唯一机器数据源；批准证据放 `Docs/03_Management/Review_Evidence/`，同步工具只校验记录，不作批准决定。若用户在聊天确认，将其原话与来源落盘后再更新状态。
冻结 R/F、已批准系统规则、跨系统契约变化使用 CR-YYYYMMDD-NNN：问题 → 来源 → 提案 → 影响系统/任务/测试 → 用户决定 → 新版本 → 覆盖同步 → 回归。CR 批准前不能实施该规则改变。
不改变玩家规则的纠错或后续测试调参可在既有授权内进行，但须记录参数版本、理由和证据；不能借“调参”更改永久堕落、结局等冻结边界。

## 5. 同步、提交与证据

每个工作单元结束前：保存已授权修改 → 登记审阅/CR/证据 → 更新 workflow_state → `python3 Tools/docs_workflow.py sync` → `python3 Tools/docs_workflow.py check` → 报告未解决项。
自动同步仅生成 PROJECT_STATUS、系统索引、实时覆盖矩阵、审阅表、T01–T16 测试索引。不会改基准、批准记录、系统正文或任务计划；不会根据文件存在推断功能完成。无后台定时器或已安装 Git 钩子。
未来 Task Registry 建立后，每个 Task 状态变化必须同步 Task Registry、测试记录、状态摘要与需求映射；在完成适配前使用人工核对，不能声称本轮工具已支持任意未来任务表。
未来测试记录至少包含：Task ID、R/F、用例、测试模式、Unity/平台版本、代码版本/脏文件摘要、复现步骤、预期/实际、运行时间、退出码、完整日志路径、截图/视频（适用）、失败和未测项。仅截图不能替代行为证据。
若已有 Git，仅暂存当前工作相关文件；提交前检查 diff 与文档校验，玩法代码提交需相应测试证据。提交信息引用 Task ID 或 DOCS/CR 与来源。用户原文件不自动纳入新提交；无 Git 时报告事实并用快照恢复，不能捏造 commit/hash。
不得擅自推送、发布、联网安装、发送他人消息或进行外部操作；本地文档工具不触发这些动作。

项目版本、平台、组员、正式截止日、Rubric 当前未知。未发现 Unity 工程不等于机器未安装 Unity；不得编造工程版本。
